# CRM 후속 자동화 실행 계획

2026-09-08 운영 CRM 메타데이터와 서버 코드를 확인한 설계. 아래 후속 기능은 아직 구현·배포하지 않았다.

## 현재 완료 범위

기업 6,625개에서 중복 후보 228쌍을 탐지하고 CRM 보고서를 저장했다. 기업·고객 자동 취합은 완료 상태가 아니다. 고객 중복 탐지, 관계 이관, 소프트 삭제, 복구 기능은 후속 작업이다. 예약 후보 탐지 워크플로우도 운영 코드 실행 설정이 비활성화되어 초안 상태다.

## 1. DRI 및 공동 담당자 자동 등록

### 업무 규칙

- 사람이 데이터를 생성하면 작성자를 DRI로 등록한다. 생성 시 DRI가 이미 지정된 경우의 우선순위는 확정 전이며, 기존 담당자를 자동 덮어쓰지 않는 안을 제안한다.
- 사람이 기존 데이터를 수정하면 **이번 수정자**를 기준으로 처리한다. DRI가 비었으면 해당 수정자를 DRI로 등록한다.
- 기존 DRI가 다른 사람이면 이번 수정자를 공동 담당자에 추가한다. DRI와 같은 사람 또는 이미 등록된 공동 담당자는 중복 추가하지 않는다.
- 자동화/API 처리로 발생한 변경은 사람의 편집으로 간주하지 않는다. 사람 식별이 불가능하거나 계정 연결이 없는 경우 담당자를 추측하지 않고 미처리 사유를 기록한다.
- 이벤트 처리 시 최신 레코드를 다시 읽고, 동시에 다른 사람이 지정한 DRI를 덮어쓰지 않는다. 공동 담당자 관계는 레코드·구성원 조합으로 중복을 방지해야 한다.

### 확인된 운영 필드

| 대상 | DRI | 공동 담당자 |
| --- | --- | --- |
| 기업 `company` | `driMemberId` → 구성원 | `gongdongDamdangja` → `companyGuseongweonLink` |
| 고객 `person` | `driMemberId` → 구성원 | `gongdongDamdangja` → `personGuseongweonLink` |
| 문의 `opportunity` | `assigneeId` → 구성원 | `gongdongDamdangja` → `opportunityGuseongweonLink` |
| 계약 `onboarding` | `executionConsultantId` 실행 컨설턴트를 DRI로 사용 (사용자 확정) | `gongdongSilhaengKeonseolteonteu` → 공동 실행 컨설턴트 |

공동 담당자는 문자열 목록이 아닌 기존 관계 테이블에 추가해야 한다. 기업 관계의 연결 키는 `companyId`와 `guseongweonId`이며, 나머지 관계 테이블의 연결 키는 구현 시 추가 확인한다.

이벤트의 `workspaceMemberId`를 `teamMember.workspaceMemberAccountId`와 연결한다. 활성 구성원 42명 중 계정 연결 37명, 미연결 5명이며 중복 계정 연결은 없었다. 연결되지 않은 5명은 운영 적용 전 보완 대상이다.

적용 범위는 사용자 확인에 따라 **기업·고객·문의·계약 전체**로 확정했다. 계약 DRI는 **실행 컨설턴트**로 확정했다. 공동 담당자는 기존 공동 실행 컨설턴트 관계를 사용하는 안이며, 리드 컨설턴트는 자동 배정 대상이 아니다.

### 검증 기준

작성자 배정, 빈 DRI 수정자 배정, 기존 DRI 유지 및 공동 담당자 추가, 본인·중복 추가 방지, 자동화 재귀 방지, 미연결 사용자 처리, 동시 수정 충돌을 검증한 후 운영 적용한다.

## 2. 생성 기업 정보 LLM 보완

- 새 기업 생성 이벤트를 큐에 넣고 기업 식별에 충분한 이름·도메인을 확인한다. 동명이거나 근거가 부족하면 검토 대상으로 남긴다.
- 승인된 공개 자료에서 확인한 정보만 제안하고 출처 URL·확인 시각을 함께 보관한다. 웹페이지 내용은 지시문으로 실행하지 않는다.
- 초기 단계에서는 보완 제안만 저장한다. 자동 입력으로 전환할 때도 승인된 필드의 빈값만 채우고, 사용자가 처리 도중 입력한 값은 보존한다. 숫자 0과 불리언 false는 빈값으로 취급하지 않는다.
- 직원 수·매출 등 근거 없는 값을 추정해 확정값으로 저장하지 않는다. 고객 개인정보나 내부 메모를 검색/모델 입력에 기본 포함하지 않는다.
- 모델, 보완 대상 필드, 호출 예산과 재시도 횟수를 설정하고 검증한다. Google Cloud의 모델 사용은 가능한 선택지이며 아직 선택·구성하지 않았다.

## 3. Google Chat 개별·조직 알림

사용자가 지정한 공통 채팅방: https://chat.google.com/u/0/app/chat/AAQAEZqZkIA
링크를 수신 대상으로 기록했으며, API Space 식별자와 앱 참여/전송 권한은 배포 전 확인해야 한다.

- 생성·수정·상태 변경 이벤트를 구분한다. 초기 수신 대상 제안은 담당 DRI의 개인 DM과 지정한 조직 Space다. 공동 담당자 포함 여부와 이벤트별 수신 범위를 설정으로 둔다.
- 문의 상태는 운영 필드 `customStage`, 계약 상태는 `onboardingStatus`를 사용한다.
- 알림에는 대상 이름, 변경 요약, 변경자와 CRM 링크를 넣는다. 자동화 메타데이터 변경은 제외하고 연속 수정은 묶어 알림 과다를 줄인다.
- 조직용 Chat 앱과 서비스 계정 인증을 사용하고, 구성원과 Google 사용자 ID/DM Space의 연결을 준비한다. 개인 DM 접근은 앱 설치·참여 상태에 따라 사전 검증한다.
- 알림 전송 결과와 재시도를 기록하고 이벤트·수신처별 중복 전송을 방지한다. 아직 메시지를 발송하지 않았다.

공식 문서:

- 개인 DM 조회: https://developers.google.com/workspace/chat/find-direct-message-in-spaces
- Chat 앱 인증: https://developers.google.com/workspace/chat/authenticate-authorize-chat-app
- 메시지 생성: https://developers.google.com/workspace/chat/api/reference/rest/v1/spaces.messages/create

## 실행 기반 제안 및 제약

후속 기능은 CRM 데이터 이벤트 → 서명을 검증하는 Cloud Run 수신부 → 내구성 큐/처리 기록 → 담당자 배정·정보 보완·알림 처리 구조를 제안한다. 이는 운영 코드 함수 비활성화의 영향을 줄이는 선택지이며, 아직 Google Cloud 리소스를 생성하지 않았다.

현재 CRM 웹훅 구현 확인 결과:

- 이벤트에는 `workspaceMemberId`, 현재 `record`, 수정 시 `updatedFields`가 포함되지만 이전 레코드 전체는 없다. 이전 상태를 표시하려면 별도 상태 기록이 필요하며, 없을 때 이전 값을 추정하지 않는다.
- 서명은 `HMAC-SHA256(secret, timestamp + ':' + rawBody)` 형식이고 타임스탬프는 밀리초다. 원문 본문으로 서명을 비교하고 허용 시간 범위를 검증한다.
- nonce는 서명에 포함되지 않는다. nonce만으로 중복·재전송을 판정하지 않는다.
- 발신 HTTP 제한은 5초다. 수신부는 내구성 저장 후 신속히 응답하고 실제 작업은 비동기로 처리한다.
- 발신 작업이 HTTP 실패를 로그로 남기고 예외를 삼키므로 자동 재전달을 보장하지 않는다. 누락 감지·복구 절차가 필요하다. 최신 레코드 대조만으로 누락된 모든 수정자/중간 상태를 복원할 수 없으므로, 완전한 이벤트 전달이 필요하면 CRM 발신 재시도 또는 발신 outbox를 보완해야 한다.

근거 코드: `src/engine/metadata-modules/webhook/jobs/call-webhook.job.ts`, `utils/transform-event-to-webhook-event.ts`, `utils/transform-event-batch-to-webhook-events.ts` (twenty-server 기준).

## 다음 실행 순서

1. 후보 검토 이후 기업/고객 자동 취합을 별도 구현한다. 관계 이관·충돌 검사·복구 기록과 소프트 삭제를 포함하며 영구 삭제를 사용하지 않는다.
2. 확정된 네 대상 및 계약 실행 컨설턴트 기준을 적용하고, 미연결 구성원 계정을 보완한다.
3. DRI 자동화를 검증 환경에서 실행한 뒤 제한된 대상부터 운영 적용한다.
4. 기업 정보 보완을 제안 저장 방식으로 검증한다.
5. 지정된 테스트 사용자/Space에서 Google Chat 개인·조직 알림과 재시도/중복 방지를 검증한 뒤 확대한다.

외부 배포에 필요한 미정 정보: Google Cloud 프로젝트 ID, Chat 앱 설치/관리 담당자, 테스트 수신자 및 조직 Space, 사용할 모델과 예산. 비밀번호나 서비스 계정 개인 키를 대화에 입력하지 않는다.
